# Task C2 Deliverable — Encryption & Masking Specification (with Defended Security Budget)

## Task C2 — Security & Privacy (C8)

**Client:** Savanna Retail Group (SRG) · **Prepared by:** Lead Enterprise Data Management Consultant
**Status:** Draft for Data Governance Council · **Version:** 1.0
**Purpose:** (a) binding technical requirements for encryption, tokenisation and masking; (b) an explicit **security slice** of the UGX 480,000,000/yr envelope (~USD 130,000; 1 USD ≈ UGX 3,700) over 18 months — **every inclusion and every omission mapped to a risk ID** from `docs/C2_threat_model_risk_register.md`.
**Regulatory anchor:** DPPA 2019 (Cap. 97) s.20 security measures, s.21 security measures re data processed by processor, s.23 notification of data security breaches (Cap. 97 consolidated numbering — verify against official gazette before external use); GDPR Art.25 protection by design, Art.28 processors, Art.32 security of processing.
**Direct driver:** the realised Jinja incident — unencrypted laptop holding an export of 9,000 customer records (names, phones, purchase history), reported internally 11 days late, **no breach notification made** (R1, R13).

### (a) Requirements specification

| Layer | Requirement | Standard / reference | Applies to | Implementation | Owner |
|---|---|---|---|---|---|
| **At rest — cloud object storage** | All buckets/objects encrypted at rest by default; no public ACLs; access logs on | AES-256 (cloud server-side encryption, SSE-AES256 or equivalent KMS-backed) | Cloud landing zone, exports, backups in cloud, analytics copies | Cloud console/IaC default encryption enabled; bucket policy denies unencrypted puts; annual access review | Head of IT |
| **At rest — laptops & HQ servers** | **Mandatory full-disk encryption (FDE)** on *any* device able to export Restricted data; screen lock ≤ 10 min; remote wipe capability | AES-256 via LUKS (Linux) / BitLocker (Windows); enforced by device-compliance policy | All staff laptops incl. store back-office devices, HQ servers, the analyst device class that produced the Jinja export | Rollout UGX ~15M (licences + config + recovery-key escrow); monthly device-compliance report; **export of Restricted data blocked on non-compliant devices** | Head of IT |
| **At rest — backups** | Backups encrypted with separate keys; restore **tested** quarterly | AES-256 + documented restore test evidence | Nightly DB dumps, ETL landings, file shares | Encrypted backup to offsite/cloud; quarterly test restore into a sandbox; results logged | IT Operations Lead |
| **In transit — general** | TLS 1.2+ everywhere (1.3 preferred); reject plain FTP, plain SMTP/email attachment flows, and HTTP admin endpoints | TLS 1.2+ (RFC 8446 baseline), modern cipher suites, cert auto-renewal | Store→HQ links, ETL feeds, POS↔warehouse sync, SavannaShop, loyalty app, partner APIs | SFTP or TLS-wrapped transfers; store→HQ **WireGuard/OpenVPN tunnels**; certificate lifecycle calendar with expiry alerts | Head of IT |
| **In transit — store links** | Where tunnels cannot be maintained during outages, transfers use SFTP with key auth — never unencrypted fallback | WireGuard/OpenVPN or SFTP | 23 stores (hours-daily offline) | Tunnel config pushed centrally; offline windows buffer locally then sync over tunnel | IT Operations Lead |
| **Application** | Parameterised SQL only; secrets in environment/secret store, never in code; no PII in logs | OWASP ASVS; DPPA s.20; GDPR Art.32(1)(b) | `srg_etl_pipeline.py`, BI queries, CRM/loyalty integrations | SQLAlchemy `text()` with bound parameters (already the ETL pattern); `.env`/secret manager excluded from git (`.gitignore` hygiene enforced in repo); log scrubbing for phone/email | EDM Consultant + IT Operations Lead |
| **Key management** | Central KMS; **annual rotation**; split custody; no developer access to production keys; documented break-glass | Cloud KMS **or** self-hosted (LibrePCA-style) HSM-less KMS | Encryption keys for storage, backups, tunnels, tokenisation | **Head of IT administers the key; CFO holds recovery-key escrow envelope**; dual-control for key export; break-glass procedure tested annually and logged; key inventory register | Head of IT (admin) / CFO (escrow) |
| **Endpoint (the direct Jinja fix)** | FDE + screen lock + remote wipe mandatory for any device able to export Restricted data; export requires approval and is logged | AES-256 FDE; device compliance policy | Laptops, store back-office PCs, any removable-media-capable device | Compliance gate: unencrypted device → no access to Restricted datasets; monthly attestation; 100% target by month 6 (CHK-09) | Head of IT |
| **Tokenisation** | `payment_ref` tokenised in analytics copies; only last-4 retained for reconciliation | Tokenisation (NIST SP 800-157 principles); least privilege | MTN MoMo / Airtel Money references (73.2% of revenue; 849/7,385 = 11.5% PENDING) | Analytics store holds `MP******89`-style tokens; full ref confined to Finance reconciliation schema accessible to Finance Reconciliation Officer (`VR-012`/`DQC-08` tie-in) | Finance Reconciliation Officer + Head of IT |
| **Masking — policy** | **Analytics copy masked by default**; raw access only via column-level GRANT to `compliance_officer` / `cdm_admin`, always audited | Consistent dynamic masking; DPPA s.10; GDPR Art.25/32 | All customer PII surfaced to analysts, dashboards, exports | Views in `module4_security/data_masking.sql`: **phone → `+256-XXX-XX1234`, name → `J*** D**`, email → `j***@domain`, `payment_ref` → `MP******89`**; default-deny GRANTs from `rbac_postgresql.sql`; RLS store scoping | Head of IT |
| **Masking — evidence** | Masking and access controls demonstrated before deployment sign-off | Executable evidence | Warehouse analytics layer | `data_masking_demo.py` executed on live data: **4/4 checks PASS**; `rbac_test.sql` **15/15 PASS** (documented *reference run* — no PostgreSQL server in the build environment; re-running on PostgreSQL 15/16 reproduces it verbatim per `rbac_test_expected_output.md`) | EDM Consultant |
| **Data-in-use (residual)** | No bulk plaintext exports to endpoints without ticketed approval; exports expire (≤ 7 days) and are watermarked | Export control policy (POL-001 companion) | Analyst ad-hoc extracts (the Jinja pattern) | Approved-export folder only; auto-delete; export log reviewed monthly | CRM Officer (approver) / Head of IT (enforcement) |

#### Defended omissions — what NOT to fund, and why

| Not funded | Why excluded (defence) | Risk accepted / alternative treatment | Residual risk accepted |
|---|---|---|---|
| **On-prem HSM** | Cost and skills far exceed need: SRG has no high-volume key ceremony, no payments key of its own (MoMo/Airtel hold the money keys), and zero data-engineering staff to operate one | Cloud KMS (B3) + split custody (Head of IT / CFO escrow) gives tamper-evident custody at ~1% of HSM cost | Low — accepted (R1, R8) |
| **Enterprise DLP across all endpoints** | Full DLP licences for 23 stores + HQ would dominate the slice for a team of 4 with no SOC to triage its alerts; classic over-control with alert fatigue | **Layered alternative:** mandatory FDE (B1) + export control & approval log + POL-001 classification + masking by default (module4) + audit logs. Blocks *and* detects the Jinja pattern without a DLP console nobody reads | Medium — accepted, reviewed at 12 months (R1, R13, R9) |
| **24/7 SOC (in-house or full MSSP)** | Permanent staffing would exceed the entire security slice annually; SRG's threat profile (retail, UGX) does not justify continuous manned monitoring | **Outsourced quarterly threat-hunt + alerting** inside B6/B7; breach plan's 1h internal reporting rule; on-call rotation for the 4-person team (CA-6) | Medium — accepted, re-scored after first pen test (R3, R4) |
| **Encrypting Public-tier data** (product names, public categories, store locations) | Encrypting non-sensitive data inflates key-management load, backup cost and query complexity while protecting nothing — classification already exists (25 dictionary attributes tagged Public/Confidential/Restricted) | Public tier stays unencrypted at field level (storage-level encryption still applies incidentally); effort concentrates on Restricted (payroll/national IDs, bulk PII) | Low — accepted by design (POL-001; GDPR Art.25/32 risk-based approach) |
| **Homegrown cryptography** | Bespoke ciphers are the single most reliable way to create a breach; no competence claim could survive a PDPO or GDPR review | Standard, vetted primitives only: AES-256, TLS 1.2+, WireGuard, established KMS | None — prohibited outright (R11, R12) |
| **Full zero-trust rollout (micro-segmentation, per-app proxying, device trust mesh)** | Right architecture, wrong maturity moment: SRG has not yet finished RBAC deployment, PDPO registration, or FDE; zero-trust on a weak base multiplies unmaintainable policy for 4 staff | **Phase later (month 18+)**: current path is default-deny DB access + RLS + MFA (B5) + tunnels (B2) — the 80% of zero-trust that fits the envelope; re-evaluate at Phase 2 catalog exit gate | Medium — accepted with a documented revisit (R3, R4, R12) |

**Every line above maps to the register:** inclusions B1–B7 defend the eight red-band risks (R1, R2, R3, R6, R9, R11, R12, R13) and the amber payment/insider risks (R4, R5); omissions either re-treat the same risks more cheaply (DLP → FDE+export control+masking; SOC → quarterly threat-hunt; zero-trust → MFA+default-deny+tunnels) or deliberately protect assets that are not sensitive (Public tier). **No risk is silently dropped.**

### Think-deeper answer

**Prompt: "Full encryption of everything is the 'safe' answer but not a strategy." Defend every omission as explicitly as every inclusion.**

Full encryption is a *slogan* because it optimises for a single failure mode (data at rest read by an unauthorised party) while pretending the budget, the people, and the other nine failure modes do not exist. Defended in order:

1. **Endpoint FDE is included (B1) — and it is the *narrow* version of "encrypt everything."** The Jinja loss (9,000 records, unencrypted, 11-day delay, no notification) is the realised 25-score risk; UGX 15M buys the control with the highest risk-reduction per shilling in the whole register. Not funding it would be indefensible; funding *only* it would repeat the error in mirror image.
2. **Public-tier data is excluded because encryption has a carrying cost.** Every encrypted field adds key-rotation surface, backup complexity, and query friction — real costs paid by a team of 4 with zero data-engineering. Wrapping product names and store locations in AES-256 protects nothing an attacker values while consuming exactly the operational attention that R12 (key-person dependency) says is scarce. Classification (POL-001, 25 dictionary attributes) is what makes targeted encryption *possible*; "encrypt everything" is what people say when classification has not been done.
3. **No on-prem HSM: custody without theatre.** SRG holds no payment cryptography (MTN MoMo and Airtel Money do), so the asset to protect is keys for storage/backups — squarely served by cloud KMS + split custody (Head of IT administers, CFO escrows). An HSM would add cost, a ceremony, and a single trained operator (R12 again) for assurance levels the PDPO audit will not ask for.
4. **No enterprise DLP: controls a four-person team can actually operate.** DLP without a triage function produces ignored alerts — a false sense of safety, which is *worse* than the absence of DLP because it suppresses vigilance. The layered substitute (export approval + logging + FDE blocking non-compliant devices + masking-by-default + classification) defends the same asset against the same vector (bulk export) with controls that fit in existing roles: `data_masking_demo.py` 4/4 and `rbac_test.sql` 15/15 prove the masking/RBAC layer already works.
5. **No 24/7 SOC: match monitoring to the threat, not to the brochure.** Continuous manned monitoring costs more annually than the entire 18-month security slice. SRG's realistic worst cases — ransomware on 23 MySQL boxes, a stolen laptop, an MoMo reconciliation gap — are detected by *thresholds and clocks* (DQC-07, DQC-08, the 1-hour reporting rule in `docs/C2_breach_response_plan.md`), not by a night watch. Quarterly threat-hunts plus alerting buy the detection coverage at ~B6/B7 prices.
6. **No homegrown cryptography: the one omission with zero residual argument.** A custom algorithm is an unpatchable vulnerability with a press release attached; PDPO (s.20) and GDPR Art.32 expect *appropriate* — i.e. standard — measures.
7. **No full zero-trust today: sequence beats ambition.** Zero-trust presumes identity, device, and policy hygiene SRG has not yet deployed (module4 is built but not in production; PDPO registration is a FAIL in `docs/C2_compliance_audit_checklist.md`). Layering a mesh on that base creates unmaintainable policy for 4 staff — the R12 failure mode industrialised. The phased subset (MFA, default-deny, RLS, tunnels) is the same destination travelled at the speed the organisation can operate.

The strategic claim, stated plainly: **a budget is an ethical document.** UGX 66M spent against named risks (R1, R2, R3, R9, R13) with defended residuals beats UGX 200M+ spent on the comforting words "encrypted, DLP, 24/7" that leave the actual Jinja laptop unencrypted, the PDPO unregistered, and the backups untested. The measure of this specification is not how much it protects in a demo — it is whether every omission still holds when the Council asks, six months from now, *who accepted that risk and why*. Here the answer is written down: yes, named, scored, and revisited.
